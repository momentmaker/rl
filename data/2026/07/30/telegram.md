🎲 *Random Learning — 2026-07-30*

Three rabbit holes, one shape: the thing that costs you is never the thing the pitch was about.

*1. Which AI video upscalers people actually run locally*
The quality argument is over, and it was never the argument that mattered. Blind tests on real 480p/720p/1080p footage put open-source SeedVR2 at *9.7/10 against Topaz's 9.8* — a gap most viewers can't see. You're choosing between a preset and a graph: Topaz is drop-in-a-file, SeedVR2 is ComfyUI plus weight management plus temporal tuning. The month's real delta is a *VRAM number*: SeedVR2-1.4B, a 6-layer distillation of the 7B (stock is 36 blocks), runs in *~4.6 GB where the teacher wants 14-16* — the difference between a card you own and one you rent. Where it falls apart is not softness, it's *invention*: "most upscalers use diffusion based models…looks nice but adds its own information." Skin comes back waxy because the model guesses detail rather than recovering it; the cheap fix is asking for 2x, not 6x. And the failure that survives every VRAM improvement is *temporal* — a per-frame upscaler decides what to invent separately on each frame, so moving subjects shimmer, often worse than the artifact it replaced. Sequence-aware models cut flicker ~57%, not to zero. Hence the counter-move: a plain Metal/GPU scaler that never recovers detail that isn't there — exactly the point for archival work.

*2. What local-first sync actually costs to run*
Not merge logic. *Tombstones.* A CRDT can't forget — deleting records the deletion, and the marker stays until you can prove every replica saw it. Figma found documents carrying *10M+ tombstones at 32 bytes each*; files became gigabytes. Generalised, overhead runs 16-32 bytes per character on top of state: a *17-33x memory footprint*. The fix quietly gives back the property people adopted CRDTs for — you can garbage-collect tombstones, but only once you know *every* replica saw the delete, which requires coordination. So teams snapshot instead (60-80% storage reduction merging Yjs updates), and every one of those numbers is a background job you now own plus a history-retention policy you have to defend. Every serious guide names the same four hard parts, none of them the merge algorithm: *conflicts, auth, storage, partial sync*. The clean disqualifier: strong eventual consistency means everyone converges, not that anyone was right — inventory where several people buy the last item merges into a state that's internally consistent and commercially wrong. Bonus: on HN this month "local-first" almost always meant a *desktop AI tool with no cloud*, not sync at all.

*3. Code ownership and blame when an agent wrote the commit*
The structural fact underneath everything: *git has no native binding between a commit and whether a human, a model, or an agent produced it.* Author fields are spoofable; SSH keys prove possession, not identity. So the whole argument is about what to bolt on — which is why it gets heated over a commit trailer. LLVM's January "human in the loop" policy is the reference text: a human must read all LLM-generated code before asking anyone else to review it, agents submitting without human approval are *forbidden*, and tool-generated content gets an `Assisted-by:` trailer, now the de facto standard. Running exactly the other way: automatic `Co-Authored-By: Claude` trailers have two open issues against them as branding user work without consent, one report of *489 commits tagged before the author noticed*, and Emacs force-pushing master to rewrite history over one. That split is about *credit*, not accountability. Sharpest detail in LLVM's policy: banning AI on "good first issue" tickets protects the *onboarding path*, not the codebase. And legally the "AI did it" defense is already closed (California AB 316, January) while purely AI-generated code *isn't copyrightable* for lack of human authorship. The code nobody can pin on you is also code you may not own.
